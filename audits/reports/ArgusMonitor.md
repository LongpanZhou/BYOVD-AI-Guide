### 1.2 Imports of security interest

The import table contains the standard WDM/PnP surface plus:

- **Memory:** `MmUnmapIoSpace`, `MmIsAddressValid`, `MmGetSystemRoutineAddress`. `MmMapIoSpaceEx` is resolved dynamically at init by name (`0x14000CE30`) into `DAT_140010BF8`; the wrapper is `FUN_14000A2BC` at `0x14000A2BC`.
- **Port/PCI/MSR:** `HalGetBusDataByOffset`, `HalSetBusDataByOffset`, `HalTranslateBusAddress`, and compiler-intrinsic `in`/`out`/`rdmsr`/`wrmsr`/`rdtsc`/`cpuid`.
- **I/O:** `IoCreateDevice` (via Wdmlib `IoCreateDeviceSecure`), `IoCreateSymbolicLink`, `IoDeleteDevice`, `IoDeleteSymbolicLink`, `IofCompleteRequest`, `IoBuildDeviceIoControlRequest`, `IofCallDriver`, `IoGetDeviceObjectPointer`, `ObQueryNameString`, `ObOpenObjectByPointer`.
- **File/registry:** `ZwCreateFile`, `ZwWriteFile`, `ZwReadFile`, `ZwSetInformationFile`, `ZwQueryInformationFile`, `ZwOpenFile`, `ZwClose`, `RtlWriteRegistryValue`, `ZwOpenKey`, `ZwQueryValueKey`, `ZwCreateKey`, `ZwSetValueKey`.
- **Security descriptor helpers:** `SeCaptureSecurityDescriptor`, `RtlGetDaclSecurityDescriptor`, `RtlCreateSecurityDescriptor`, `RtlAddAccessAllowedAce`, `RtlSetDaclSecurityDescriptor`, `ZwSetSecurityObject`, `SeConvertStringSecurityDescriptorToSecurityDescriptor`. These are part of the statically linked Wdmlib device-creation path, not caller-authorization checks.

The driver is a WDM hardware-monitoring driver with a statically linked Wdmlib. The presence of `wrmsr`, `rdmsr`, `HalSetBusDataByOffset`, and direct port I/O is the dominant risk, not a traditional IRP write path.

### 1.3 Application-level framing

All device controls are `METHOD_BUFFERED` and `FILE_ANY_ACCESS` (see §3). Most requests are additionally framed with a proprietary 16-bit CRC and a 0x200-byte XOR keystream:

- `FUN_140001044` (`0x140001044`) verifies the last two bytes of an input buffer as a CRC-16 (polynomial `0xA001`, reflected) and, when the mode byte is 1, XOR-decrypts the payload with `DAT_1400113E0`.
- `FUN_140002D18` (`0x140002D18`) appends the CRC and XORs output.
- The keystream is generated by the "auth" IOCTL and is global, not per-client.

This is obfuscation, not authentication (see §4.3).

### 2.3 Create / close

- **Create** `FUN_1400011F0` (`0x1400011F0`): reads the file object from `IRP+0xB8`→`+0x30`, gets `FileName` at file object `+0x58`, and requires it to equal `\main` or `\hdd`. `\main` is a global singleton (`DAT_1400113C8`); `\hdd` is only allowed for the same EPROCESS/PID/create-time that opened `\main`, and only once (`DAT_1400113C9`). On success it allocates a 0x20-byte client context with tag `AMCX` (`0x414D4358`), stores the raw EPROCESS pointer, PID and create time, allocates global 0x280 (`AMM2`) and 0x1800 (`AMM3`) buffers, and completes with `Information = 0`. Evidence: `ev_4be48d5e9f6b43554a25eb350978a0280db45d2766739556416a473c2663354f`.
- **Close** `FUN_1400010D0` (`0x1400010D0`): on the last close, frees the global buffers, calls `FUN_14000425C(5,...)` to unmap all MMIO windows, clears the main/secondary flags, frees the client context with `AMCX`, and completes. - **Unload** `FUN_140002CD0` (`0x140002CD0`): deletes `\DosDevices\ArgusMonitor`, walks the device object list and deletes each device. Evidence: `ev_ca44f8fdf47198d9f076585c368a550b4f9d03ad71ac59ab635e66cf0bb0c5d8`.

### 2.4 Dispatch

`FUN_1400014A0` (`0x1400014A0`) is the only device-control entry point. No `IRP_MJ_READ`, `IRP_MJ_WRITE`, or `IRP_MJ_INTERNAL_DEVICE_CONTROL` handler is installed.

It performs, in order:

1. Fetch the client context from the file object: `*(fileObject + 0x18)`. Null → `0xE000A160`.
2. `IoGetRequestorProcess(IRP)`, `PsGetProcessId`, `PsGetProcessCreateTimeQuadPart`; require exact match to the stored EPROCESS pointer, PID, and create time. Mismatch → `0xE000A161`/`0xE000A162`/`0xE000A163`.
3. Read `InputBufferLength` (IO_STACK `+0x10`), `OutputBufferLength` (`+0x8`), and `IoControlCode` (`+0x18`).
4. Compare the code and both lengths. Most paths then require `DAT_140010BE1 != 0`; otherwise `0xE000A008`.
5. Verify the input CRC/XOR with `FUN_140001044`; failure → `0xE000A009`.
6. Optionally wait on an event (`FUN_140001000`, up to 1 second) to serialize hardware access; timeout → `0xE000A003`.
7. Call the handler, write `IoStatus.Status` and `IoStatus.Information`, release the event, and `IofCompleteRequest`.

Evidence: `ev_60e18d991866e74fcd890ac7ba8386604358fb0afc24f4191e7411df69795472` (pseudocode), `ev_97920b20bb333907f598c1732670caf706144e97480b35a13bbae56c02edee7c` (instructions).

## 3 IOCTL table

### 3.1 Encoding

Every code compared in the dispatcher is of the form `0x9C40xxxx`:

- **DeviceType** (bits 31–16): `0x9C40`.
- **Access** (bits 15–14): `0` → **FILE_ANY_ACCESS** for all 38 codes.
- **Function** (bits 13–2): per-code index.
- **Method** (bits 1–0): `0` → **METHOD_BUFFERED** for all 38 codes.

Therefore the I/O manager allocates one system buffer of `max(InputBufferLength, OutputBufferLength)`, copies input in, and copies output back. The driver never reads `Type3InputBuffer` or `Irp->UserBuffer`; there is no `METHOD_NEITHER` path, no `ProbeForWrite`, and no direct user-pointer dereference in the main data path. The only authorization on the handle is the device DACL; the IOCTLs themselves carry `FILE_ANY_ACCESS`.

The dispatcher enforces both lengths before invoking a handler. The 0x280-output handlers copy 0x200 bytes; the 0x610-output handlers query/write at most 0x610. ## 4 Access-control audit

### 4.1 DACL and open path

The SDDL is passed as the `DefaultSDDLString` argument to `IoCreateDeviceSecure` at `0x14001505A`–`0x140015076`, with `DeviceCharacteristics = 0x100` (`FILE_DEVICE_SECURE_OPEN`). The resulting DACL is:

```
D:P(A;;GA;;;SY)(A;;GA;;;BA)(A;;GRGW;;;AU)
```

- `SY` (LocalSystem) and `BA` (Builtin Administrators): generic all.
- `AU` (Authenticated Users): generic read + generic write.
- Protected DACL (`P`), no inherited ACEs.

This is consistent with the known triage. Any authenticated local user can open the device with read/write access. The symlink `\DosDevices\ArgusMonitor` makes it reachable as `\\.\ArgusMonitor\<name>`.

### 4.2 No caller-authorization checks

The driver does **not** call `SeAccessCheck`, `SeSinglePrivilegeCheck`, `SeExports`, or any equivalent privilege test. The security-descriptor imports (`SeCaptureSecurityDescriptor`, `RtlGetDaclSecurityDescriptor`, `RtlCreateSecurityDescriptor`, `RtlAddAccessAllowedAce`, `RtlSetDaclSecurityDescriptor`, `ZwSetSecurityObject`) belong to the Wdmlib `IoCreateDeviceSecure` implementation and are used to create/apply the device SD, not to authorize a caller.

The create handler does not inspect `DesiredAccess`, `FILE_WRITE_ACCESS`, or the security context. It only checks the file name (`\main`/`\hdd`) and process identity. Because every IOCTL is `FILE_ANY_ACCESS`, a handle opened with only read access would still be able to issue write-like IOCTLs. In the current SDDL, `AU` has `GRGW`, so this is a defense-in-depth gap rather than an additional bypass.

### 4.3 The "auth" IOCTL is not authentication

`0x9C4024C4` is the only code that does not require `DAT_140010BE1`. Its logic:

1. `FUN_140001044(buf, 0x28, 0)` verifies the CRC-16 at buf+0x26. Before authentication the XOR mode is 0, so this is a plain checksum, not a secret.
2. It copies the first 0x20 bytes to a local seed and calls `FUN_14000B154(seed, 0x20, stats)`.
   - `FUN_14000B154` is **not** a cryptographic verifier. It computes simple statistics: distinct-byte count, min/max range, monotonic-run flags, all-equal/alternating/period-4 flags, and accepts inputs that look "random" (range > 0x2F, distinct count > 0x0F, no run/period patterns).
3. `FUN_14000ABD4` builds a 32-byte key from **static** `.rdata` constants:
   - `0x14000E400` XOR `0x14000E420` → first 32 bytes.
   - `0x14000E440` XOR `0x14000E460` → second 32 bytes.
4. `FUN_14000AC88` runs a SHA-256-based KDF (`FUN_14000A4D8`) over key‖seed‖counter for 16 blocks and writes 0x200 bytes to `DAT_1400113E0`. It returns success whenever the parameters are valid; there is **no comparison to a stored secret or signature**.
5. At `0x1400017AB`, `MOV byte ptr [0x140010BE1], 1` sets the global auth flag.

Evidence: `ev_ec48a2757c7737f313c4903720beda4308a2583f52b64c41fb7484ad450c1224`, `ev_a1ff52c7e91ad566155a57070a5ac11d81ccbee124088afba5ba375ffa8664a5`, `ev_bbd333d99adf0635d9242f5333811d40c1261301585c33b9cd1a4c5b59f937dd`, `ev_128d1f510a69b6fc9603dd255e7d131d77d44be16846d25f02f113328f3cdf62`, `ev_281b02184d4110e91190226f743ee26f695a06e2b906ff89168739cbe5a9aace` (static key bytes).

**Conclusion:** any authenticated local user who can open `\main` can send 0x28 bytes containing 0x20 random-looking bytes plus a valid CRC, set `DAT_140010BE1`, and derive the same 0x200-byte keystream. The handshake is a deterministic client-obfuscation protocol, not an authorization boundary.

### 4.4 Process binding and global state

The create path stores the raw EPROCESS pointer, PID, and create time in a 0x20-byte context. The dispatch path requires all three to match the current requestor. This prevents a different process from using a stolen handle, but it does not stop a local user from opening the device themselves when `\main` is free.

`\main` is a global singleton (`DAT_1400113C8`); if the legitimate vendor application is running, a second opener gets `STATUS_ACCESS_DENIED`. That is an availability/contention property, not a privilege boundary. When the vendor application is not holding the device, any `AU` user can become the client.

The auth flag and keystream are global and are **not cleared on close** (the close handler only clears the client flags and frees the per-client buffers). The auth IOCTL rejects a second call with `0xE000A172` once `DAT_140010BE1` is set. Consequently, the first client to authenticate pins the keystream for the lifetime of the loaded driver. An unprivileged user who authenticates first can lock the legitimate application out (its frames will fail the CRC/XOR check) and retain control of the interface until reboot. This is a persistent device-takeover / denial-of-service condition.

### 4.5 Reachability summary

An unprivileged authenticated user can reach the full IOCTL surface provided that:

1. the device is openable (no other `\main` client), and
2. the user sends a valid `0x9C4024C4` frame.

Both conditions are under the user's control on a system where the vendor application is not currently holding `\main`. The DACL does not require administrator or a service SID.

## 5 Most dangerous exposed capability

### 5.1 Primary: WRMSR (`0x9C4024A8`)

`FUN_14000A494` at `0x14000A494` is a direct wrapper around the `wrmsr` intrinsic:

```c
uVar1 = FUN_14000A320(msr_index, 1);   // write allowlist
if ((char)uVar1 == 0) return STATUS_ACCESS_DENIED;
wrmsr(msr_index, value);
```

The dispatcher passes:

- `msr_index = *(uint32_t *)SystemBuffer` (offset 0x00)
- `value      = *(uint64_t *)(SystemBuffer + 0x20)` (offset 0x20)
- input length 0x38, output length 0

`FUN_14000A320` (`0x14000A320`) only permits **MSR 0x38D** and **MSR 0x38F** for writes, and only when `DAT_140011380 == 1` (Intel). AMD writes are rejected. MSR 0x38F is the Intel `IA32_PERF_GLOBAL_CTRL`; both indices are performance/uncore MSRs, not paging or control-flow MSRs (no `LSTAR`, `STAR`, `CSTAR`, `SYSENTER`, `EFER`, etc.). Evidence: `ev_f0130c16baea706edcfae53e441a6f58a56d2a1a277733520cb4eef494fbea13`, `ev_81991f0b1980cd1955dcf3e84b9b28d8dab758030d304e6744a63a354fe143c6`.

**Is it a true unprivileged kernel memory write?** No. It is a genuine ring-0 write to a CPU MSR with a caller-controlled 64-bit value, but the MSR indices are allowlisted and are not kernel memory mappings. It is a privileged hardware write, not a kernel memory corruption primitive.

### 5.2 Physical-memory mapping (`0x9C4029C0` / `0x9C402D9C`)

`FUN_14000425C` (`0x14000425C`) maintains a 16-entry table at `DAT_140010CC0` (stride 0x28):

```
+0x00 physical address
+0x08 bus number
+0x0C size
+0x10 cache type
+0x14 state
+0x18 magic 0xAA5512E7
+0x20 mapped kernel VA
```

Command 2 (reachable via `0x9C4029C0`) calls `FUN_140004058` to resolve a **fixed** chipset window:

- **Intel:** reads PCI config 0:0:0 offsets 0x48/0x4C (MCHBAR), masks `0xFFFFFC000`, requires `0xFE000000 ≤ base < 0xFFFF0001`, then maps `base + 0x59B0`, size 0x20.
- **AMD:** `rdmsr(0xC0010058)` (MMIO configuration base), then maps `base + 0xC30A4`, size 4.

`FUN_14000A2BC` (`0x14000A2BC`) calls the dynamically resolved `MmMapIoSpaceEx(phys, size, 0x202/0x204)`; `FUN_1400044F0` (`0x1400044F0`) reads 4 bytes at a caller offset with `MmIsAddressValid` and a `size - 4` bound check. `FUN_140004580` (`0x140004580`) is the only MMIO-write helper and is called only from the internal SPI path (`FUN_140009544`), never from a user IOCTL.

**Is it a true physical-memory mapping?** Yes, a kernel VA mapping to physical memory is created, but it is a **fixed-window, hardware-derived** mapping, not a general `MmMapIoSpace` of a caller-chosen physical address. The user chooses only an index 0–3. `0x9C402D9C` is read-only. There is no user-reachable MMIO write to the mapped window. Evidence: `ev_3ed035264ccfef7da5478a392b6780c5ccfe24ffa182c1f365ec601db855b650`, `ev_a53369c31882cd629870a0e0dfdc9cdb19ff370bdda7035f1121b48cd12f8435`, `ev_49052b270614e67467e5f8fdcfc3d086d2d2817edfd345b3b151127376ea6da1`, `ev_7053446626e27f0ca7fabd51c03ddc4f9737de83801790f53e93b4b7a6600db1`.

### 5.3 Other privileged hardware writes

These are reachable after the bypassable auth and are more destructive to platform state than the MSR write, although none is a kernel memory write:

- **SMBus block write — `0x9C4030F8` → `FUN_140009684`:** caller controls SMBus bus/device/offset/length/data. Can write SPD/EEPROM and other persistent platform state. Evidence: `ev_ac0c908d1035df3951d3205ffba34253cee219af1a7c807e0c779fc3074d49ee`.
- **EC port I/O — `0x9C402918` / `0x9C403D8C`:** caller bytes are written to ACPI EC command/data ports 0x66/0x62 (`out`/`in` wrappers `FUN_14000C490`/`FUN_14000C30C`). This can alter EC RAM, fan/thermal policy, or hang the machine. Evidence: `ev_76f41b7bb3ea01bc79de05312a2068251fd46a57bf7704e7bb1283d8ce47c175`, `ev_e0118730ad3da83180121292eba330ead67f5abad6625bd18eae7f47c1a3af0b`, `ev_f137f1f953dac0f5d8a761afd8f8f5166332ca1f5b8e210d598e427c50bf7ad2`, `ev_42a64a34dcfc01b241d0487758248a159c686a149288c4488ec98cce819a61ca`.
- **AMD PCI config write — `0x9C403254` → `FUN_140004B8C`:** writes a caller-supplied dword through `HalSetBusDataByOffset` to AMD northbridge offsets 0x60/0xB8/0xE0, after checking vendor ID 0x1022 and CPU family/model. The accepted values are heavily constrained (0x59800, 0xD8200CA4, or 0x59800–0x59B38), so it is not an arbitrary PCI config write. Evidence: `ev_8899b17363bd005e440175f5043614b873c7de4518470bed365e6d9a0c2023aa`.

### 5.4 Kernel memory safety issues found (read-only)

These are not writes, but they are the only kernel-memory-safety defects found and are worth recording:

1. **OOB pool read in the file-write path (`0x9C402410` → `FUN_14000BCB8`).**
   - The dispatcher passes `data = SystemBuffer + 0x1F0`, `length = *(uint32_t *)(SystemBuffer + 0x1F8)`, with `IN = 0x200`, `OUT = 0`.
   - `FUN_14000BCB8` checks `length + 4 <= 0x200` (`0x14000BCF0`–`0x14000BCF8`), i.e. `length <= 0x1FC`.
   - The data pointer is already at offset 0x1F0 of a 0x200-byte system buffer. A length of 0x1FC reads through offset 0x3EB, i.e. up to **0x1EC bytes past the allocation**.
   - The bytes are written to a caller-supplied path via `ZwCreateFile`/`ZwWriteFile`, but only if the SHA-256 of the **uppercased basename** equals the fixed digest at `0x14000E4B8` (`02AE5AA3...`). The basename preimage was not recovered statically. If the fixed basename is known, the attacker can choose a user-writable directory and obtain a file containing adjacent kernel pool bytes. This is a kernel pool information leak, not a write.
   - Evidence: `ev_f65d849bbd33e9bf081cedea43f2fd44a2a6251e47422eb516bee6816b714739`, `ev_790d46e4773675ca1bfc55b94bb7645f991b2048a48be69ae88cc807295506cd`, `ev_9c682b816625081c2442f1916246b6c3bdb4c29e57bf23cab62321d2f9e5d31f`.

2. **Caller-controlled UNICODE_STRING Buffer in the registry-write path (`0x9C4036CC` → `FUN_14000C05C`).**
   - The dispatcher passes `path = local_2b8` (initialized from `SystemBuffer`), `valueName = SystemBuffer + 0xD0`, `data = SystemBuffer + 0xF8`, `length = *(uint32_t *)(SystemBuffer + 0x1F8) <= 0x100`.
   - `FUN_14000C05C` calls `RtlWriteRegistryValue(0, path->Buffer, valueName, REG_BINARY, data, length)`.
   - `valueName` is treated as a `PUNICODE_STRING`; its `Buffer` field at `SystemBuffer + 0xD8` is caller-controlled and is not validated. `RtlWriteRegistryValue` will read `Length` bytes from that pointer to form the value name. This is an **arbitrary kernel address read** (subject to the usual invalid-address fault behavior), and the result can be persisted as a registry value name.
   - The write is gated by the SHA-256 of the **full path** matching the fixed digest at `0x14000E4D8` (`A6BCAF51...`). The path preimage was not recovered statically. If the fixed key path is readable by the caller, the leaked name can be queried back; otherwise the primitive is a crash/DoS vector.
   - Evidence: `ev_8d768196957caa8dbf7ad2639c2cf5f8c0005c9aa75c5eada0201a19aa11ae0b`, `ev_d83762492135a4a0a58422a2fabeafa05c834feb2b7034d31cc6d05170122bda`, `ev_a242feb4c8a837a8c81179aae546d4721e5d552ec51b9ebe7ea02394b35eb7e7`.

No caller-controlled kernel **write** was found. In particular, there is no `MmMapLockedPagesSpecifyCache`, `ZwMapViewOfSection`, `METHOD_NEITHER` user-pointer write, `memcpy` to a user-supplied kernel address, or write loop over a caller-provided pointer. The `0x9C402410` and `0x9C4036CC` issues read from attacker-influenced addresses but do not write to them.

### 5.5 Single most dangerous capability

The single most dangerous **directly callable** primitive is **IOCTL `0x9C4024A8` (WRMSR)**: after the trivial `0x9C4024C4` handshake, an unprivileged authenticated user can write an arbitrary 64-bit value to Intel MSR 0x38D or 0x38F in ring 0. It is a true unprivileged **kernel-mode hardware write**, but it is **not a kernel memory write**. The most destructive hardware paths are the SMBus block write (`0x9C4030F8`) and the EC port writes (`0x9C402918`/`0x9C403D8C`), which can alter persistent platform state. The physical-memory mapping (`0x9C4029C0`) is real but fixed-window and read-only from user mode.

## 6 VERDICT

**No — this driver does not provide a true unprivileged kernel memory write.**

Findings:

- The device is created with an active, permissive DACL: `AU` gets `GRGW`. Any authenticated local user can open `\\.\ArgusMonitor\main` when the vendor application is not holding it.
- The "authentication" IOCTL `0x9C4024C4` is a deterministic obfuscation handshake. It checks only the randomness of a caller-chosen 0x20-byte seed and derives a 0x200-byte XOR keystream from **static** `.rdata` key material. There is no secret comparison. An unprivileged user can therefore set `DAT_140010BE1` and use the full IOCTL surface.
- After that, the user reaches genuine ring-0 hardware operations:
  - `WRMSR` to Intel MSR 0x38D/0x38F (`0x9C4024A8`);
  - SMBus block writes (`0x9C4030F8`);
  - ACPI EC port writes to 0x66/0x62 (`0x9C402918`, `0x9C403D8C`);
  - constrained AMD PCI config writes (`0x9C403254`);
  - a fixed-window `MmMapIoSpaceEx` mapping (`0x9C4029C0`) with a read-only user path (`0x9C402D9C`).
- No general physical-memory mapping and no caller-chosen physical address were found. The mapping bases are MCHBAR+0x59B0 (Intel) or TOM2+0xC30A4 (AMD); the user chooses only an index 0–3.
- No caller-controlled kernel memory write was found. The kernel-memory-safety defects are **read-only**: the OOB pool read in `0x9C402410` (up to 0x1EC bytes past a 0x200-byte system buffer, if the fixed basename hash is satisfied) and the arbitrary value-name read in `0x9C4036CC` (if the fixed registry path hash is satisfied). Both are gated by fixed SHA-256 digests whose preimages were not recovered statically.
- The auth flag and keystream are global and survive close. The first client to authenticate pins the keystream and can lock the legitimate application out until reboot — a persistent device-takeover/DoS condition.

**Risk rating:** High for hardware integrity, platform stability, and kernel information disclosure; **not** a kernel memory corruption/write primitive.

**Recommended remediations (defensive):**

1. Restrict the device DACL: remove `AU`, grant access only to the vendor service SID (or `SY`/`BA`), and do not rely on the file-name gate as authorization.
2. Replace the deterministic handshake with a real per-client authentication whose secret is not embedded in the driver; bind the key to the client context, not a global.
3. Clear the auth flag and keystream on last close; reject a second auth only after a proper per-client state reset.
4. Check `FILE_WRITE_ACCESS` (or the `DesiredAccess` in the create IRP) before permitting write-like IOCTLs.
5. Fix `FUN_14000BCB8`: require `length <= 0x10` for the buffer at `SystemBuffer + 0x1F0`, not `length + 4 <= 0x200`.
6. Validate the `UNICODE_STRING` at `SystemBuffer + 0xD0` (Length ≤ MaximumLength, Buffer inside the system buffer) before passing it to `RtlWriteRegistryValue`.
7. Reduce the hardware surface: remove `WRMSR`/SMBus/EC/PCI-config IOCTLs or require an administrator/service privilege for them.

## 7 Limitations

- **Static-only:** the driver was not loaded, no IOCTL was executed, no service was created, and no dynamic crash/leak testing was performed. The conclusions are code-reading conclusions, not runtime proofs.
- **Shared REA session:** the REA backend was concurrently used by other audits and switched active programs during the analysis. All cited evidence IDs were captured from the ArgusMonitor target before the switches; one later re-query failed against a different active program and was discarded. No evidence from other drivers is used in this report.
- **Decompiler artifacts:** Ghidra 12.1.4 pseudocode and function boundaries may be imprecise. Types such as `undefined1 (*)[16]` are decompiler reconstructions. The assembly at the cited addresses was used to disambiguate the critical buffer/pointer operations.
- **No PDB/types:** the PE references `ArgusMonitor.pdb` but no PDB was available. Structure field names and some handler semantics are inferred.
- **Hash-gated paths not recovered:** the fixed SHA-256 digests at `0x14000E4B8` and `0x14000E4D8` are recorded, but their preimages (file basename and registry path) were not recovered. Exploitability of the `0x9C402410` OOB read and the `0x9C4036CC` arbitrary read depends on satisfying those gates; the report therefore treats them as conditional.
- **Hardware-dependent semantics:** MSR 0x38D/0x38F, the AMD PCI config offsets 0x60/0xB8/0xE0, and the SMBus/EC paths are CPU/chipset-specific. Their exact effect was not validated on hardware.
- **ATA pass-through handlers:** the `\Device\HarddiskN\Partition0` handlers were reviewed for buffer bounds and command construction, but the full ATA/SMART command semantics were not modeled.
- **No proof of exploitability:** the report identifies reachable primitives and missing checks. It does not provide a working exploit, and some primitives may be constrained by platform firmware, IOMMU, or the vendor application holding `\main`.
