### 2.1 IOCTL 0x2f4017 and 0x2f8013: entry-list double fetch (primary finding)

Path: `IRP_MJ_DEVICE_CONTROL` -> `FUN_140006ac0` -> 0x2f4017 (line 4919) -> `FUN_140004ea0` (3375-3460): per-open context lookup (3388), request object from an SLIST (3397), `FUN_140002c1c(request, IRP, dir=0, LockOp=0)` (3410), forward to the lower device with completion `FUN_140006190`. Or 0x2f8013 (line 4922) -> `FUN_140005128` (per-open lookup at 3519), `FUN_140002c1c(request, IRP, dir=1, LockOp=2)` (3549).

`FUN_140002c1c` (1477-1592):

1. Locks the IRP buffer (`FUN_140001114`, line 1493). The buffer is a user buffer for user requests, mapped into kernel space by `MmMapLockedPagesSpecifyCache`.
2. **Pass 1** (lines 1505-1521). Walks the buffer as a sequence of variable-size entries. Each entry size is read from user memory (`*puVar4`, 1519) and used to advance the cursor (1520). The walk stops once the sum of sizes reaches the IRP length (`uVar2`, which comes from `IoStack`, not from the user buffer). The count of entries is stored in `*param_1` (1522). A zero-size entry never advances the sum, so the loop does not terminate (**DoS**, no race needed).
3. If count < 2 (1534): one entry is locked through `FUN_1400011f8`. No arrays are allocated, and there is no second pass.
4. If count >= 2 (1541-1544): two `NonPagedPoolNx` arrays are allocated, of `count * 4` bytes ('CASH') and `count * 0x40` bytes ('CASM'), and the second array's holders are zeroed (`FUN_140001000`).
5. **Pass 2** (lines 1560-1582). Walks the same user buffer again. The loop condition is the sum of the **re-read** entry sizes against the IRP length (1580). For each entry it:
   - writes a DWORD copied from the entry's length field (`+0x20` or `+0x24`, chosen by direction) into `arr1[uVar9]` (`arr1` is the first array; line 1566-1567);
   - locks the entry's VA and length into holder `arr2 + uVar9 * 0x40` (`FUN_1400011f8`, line 1573), with AccessMode = `IRP->RequestorMode`;
   - increments `uVar9` (1579).
   Nothing in pass 2 compares `uVar9` with the count from pass 1.

Consequence: if the user changes the entry sizes between pass 1 and pass 2 (a concurrent writer to the same user memory), pass 2 can run more iterations than pass 1 counted. It then writes past the end of both arrays. Each out-of-bounds index writes:

- a DWORD at `arr1 + 4 * k` (value chosen by the caller, from the entry's length field);
- a 0x40-byte holder record at `arr2 + 0x40 * k`. Its fields are the caller's VA (+0x28), the caller's length (+0x10, copied from +0x20 or +0x24), the holder flags, and kernel-generated values: the MDL pointer from `IoAllocateMdl` and the mapped system VA from `MmMapLockedPagesSpecifyCache` (`FUN_140001030` writes them into the holder).

Classification: a **pool buffer overflow in NonPagedPoolNx, with caller-chosen DWORD and VA/length values and kernel pointers**. The write index is sequential (+1 per entry), so the target offsets are regular. The adjacent pool layout is not controlled statically. Under `audits\scope\SEVERITY.md` this is a **W2** kernel write (constrained target and value, race-gated), rated **MW3** (section 4). The overflow is real, and it is conditional on (a) the effective device DACL admitting the caller, (b) the race, and (c) pool layout.

Note: when count = 1 the array path is skipped, so the overflow needs count >= 2 in pass 1 and more entries in pass 2.

### 2.2 IOCTL 0x2f001b (`FUN_140004cc0`): kernel-VA read oracle, no write

Path: 0x2f001b (line 4910) -> `FUN_140004cc0` (3279-3355).

- Per-open context lookup (3297). Failure returns early.
- Locks `IoStack+0x20` (Type3InputBuffer, a caller VA) with length `IoStack+0x10` (caller-chosen, 3307). **AccessMode = KernelMode**, so `MmProbeAndLockPages` does not probe the user range. Any valid kernel VA range is accepted, and so is a user VA.
- If the locked length is 1, 2, 4 or 8 (lines 3327-3334), the driver reads that many bytes from the mapped VA and sets a flag in the context to `(value == 0)` (3342, `FUN_1400079b0`).
- The flag is readable by the caller through KS property handler `FUN_140001270` (`FUN_140001270` 295-385 reads the 4-byte value at context +0x3f1c, line 335).

Classification: a **one-bit read oracle at a caller-chosen kernel address** (zero or nonzero), with no write. Verdict contribution: NO-MEMORY-WRITE for this branch. An invalid kernel range makes the probe raise, and the function has no visible exception handler. That is a **DoS** candidate (**NEEDS-DYNAMIC**).

## 4. Verdict and dynamic confirmation plan

**Verdict: MW3 - reach=R1 setup=hardware write=W2 load=signed (static, conditional).**

- **Primitive.** IRP_MJ_DEVICE_CONTROL 0x2f4017 or 0x2f8013, with METHOD_NEITHER buffers, leads to an entry-list walk in `FUN_140002c1c` that reads the same user memory twice. The second pass writes past two `NonPagedPoolNx` arrays, with caller-chosen DWORDs and caller-chosen 8-byte VA and 4-byte length values, plus kernel-generated MDL and mapped-VA pointers in the holder records.
- **Target constraints.** The write index is sequential from 0 and is not bounded by the pass-1 count. The overflow length is set by the number of pass-2 iterations, which depends on the entry sizes the caller writes during the race. The write target is whatever pool object follows the arrays. Its identity is not controlled statically.
- **Value constraints.** DWORD values are the caller's entry length fields (+0x20 or +0x24). Holder VA (+0x28) and length are the caller's entry fields. Holder MDL and mapped-VA fields are kernel-generated. The entry sizes (+0x00) control only the walk positions, not the written values.
- **Gates.** (a) The caller can open the unnamed device (effective DACL, unknown). (b) A per-open context exists (any successful CREATE). (c) A second user thread rewrites the entry sizes between pass 1 and pass 2 (race). (d) Count >= 2 on pass 1.
- **Hardware gate.** The driver attaches to a device stack in `AddDevice`, so a device must exist (see section 5). If the device can exist without hardware (not established), the matrix gives MW2 (R1, setup none, W2). The device-not-present cap keeps the hardware-gated case at MW3.

**Dynamic confirmation (described only, not run):**

1. Confirm the effective DACL of the unnamed device object and of its interface symbolic link, after the device exists. This decides the reach tier (unprivileged versus local administrator).
2. Confirm which PnP path creates this device (a binding INF or hardware IDs for this binary), and whether the `USB\DUMMYDEVICEHERE` branch in `FUN_140005638` (lines 3785-3797) provides a device without hardware.
3. Confirm, on a test build with the device present, that the second-pass count can exceed the first-pass count when the user buffer changes between passes, and what pool classes the 'CASH' and 'CASM' allocations fall into.
4. Confirm the exception behavior of `MmProbeAndLockPages` for an invalid kernel range in the 0x2f001b path (DoS versus handled failure).

## 5. Limitations

- **Binding and setup.** The supplied INF (`CorsairGamingAudio64_64D31B6E.inf`) is an APO extension package. It does not reference this `.sys`, has no service or KMDF section, and has no `Security` line. The binding INF and the hardware IDs for this binary were not located among the supplied files. Setup is recorded as hardware (inferred).
- **Effective DACL.** Not determined statically (section 1). This is the main unknown for the reach tier.
- **KS.SYS.** `KsPropertyHandler` and its descriptor and buffer checks were not analyzed. The three property sets were partly decoded from pointer data. The KS handler list in section 1 is what the dump shows. Some handler names were not individually resolved, and the call-site list in section 2 covers only the sinks visible in the dump.
- **Race and pool layout** are inferred from the code. The overflow was not executed.
- **MmProbeAndLockPages and MmMapLockedPagesSpecifyCache** semantics (MDL validation, RequestorMode probing, exception behavior) are assumed from their documented behavior and were not evaluated.
- **FUN_140003808** (device-by-name) takes its name from the requester's device map. Its name-copy bounds (2276-2279) were checked, but the full device-map path was not traced.
- **`USB\DUMMYDEVICEHERE`** (`FUN_140005638` 3785-3797) sets a per-device marker at `param_1[0x59]`. The consumer of that marker was not traced.
- **Registry write** through `FUN_140007f04` (`ZwSetValueKey`) was not analyzed for control of the key path.
